auto-onion — how it works

A bare-bones, memory-free distillation of my larger project omnididdy: a self-improving code-search engine that climbs a benchmark by having two LLM loops edit one file, scored by a frozen harness they can't touch. The layered loops are why it's an "onion."

THE SYSTEM · ONE EDIT SURFACE, TWO LOOPS

◆ SECOND LOOP (L2) · bigger model — Sonnet
Proposes a structurally new architecture by rewriting solution.py (the edit surface). e.g. greedy → ILP → Lagrangian relaxation.
↓   hands the new architecture to the inner loop to tune
● GROUND LOOP (L1) · smaller model — Haiku
Tunes the parameters of that architecture over many cheap iterations. Each candidate runs in a sandboxed subprocess; keep-if-better, else revert.
↓   report the best score reached after tuning
✓ JUDGE BY THE TUNED CEILING
The architecture is kept only if its post-tuning best beats the incumbent. The second loop then builds its next idea on the winner.
Why two loops? — the autoresearch pitfall. A single autoresearch loop only nudges parameters, so it plateaus on the very first architecture it's given. auto-onion's second loop makes structural leaps, and crucially it judges each one by its score after the inner loop has tuned it — comparing optimized vs. optimized, not first-draft vs. first-draft. That's how it escapes the local optimum a flat loop gets stuck in.

Q1 · WHY I BUILT THIS — problem & insight

Improving any solver or model is a slow human loop: think of an idea → code it → measure it → keep or throw it out → repeat. The bottleneck is the human in that loop. That loop is mechanical enough to hand to an LLM — but a single loop plateaus because it only tweaks parameters. The fix is two loops: an inner loop tunes, an outer loop proposes a structurally new approach and judges it by its tuned ceiling.

Q2 · HOW IT WORKS — execution & technical work

Two LLM loops edit one file, scored by a frozen harness. Ground loop (L1, Haiku) tunes parameters, keep-if-better else revert, each candidate in a sandboxed subprocess. Second loop (L2, Sonnet) proposes a structurally different architecture, judged by the best score it reaches after tuning. The ★ Demo button loads a finished real-engine run (set-cover: greedy 26% gap → ILP → Lagrangian = 55% better, with a tabu-search branch reverted by the gate). The ▶ Run the system button actually runs it live through the local Claude CLI — Sonnet proposes, Haiku tunes, the tree builds in real time (no API key).

EVALUATION & EVIDENCE

Reproducible: python run.py --mock is deterministic — +17.07% every run, zero API calls (I caught and fixed a real stale-bytecode nondeterminism bug getting there). Real runs: the set-cover / max-cut demos are genuine engine output imported from the parent project, disclosed in the README. Honest limits: the search is greedy with no long-term memory, and the hard-benchmark trees were produced by the parent engine and imported.

Q3 · USE CASES / IMPACT

Anything with a fitness signal: solvers, heuristics, ML-training code, GPU kernels, even prompts. It lets one person run automated R&D that used to need a team — the "scale yourself" idea made concrete.

Q4 · WHAT I'D ADD NEXT

The memory I deliberately trimmed: an archive of rejected ideas plus diversity-driven search, so it explores instead of just hill-climbing. And a clean benchmark abstraction to plug in more substrates — e.g. CIFAR image classification — behind the same two loops.
